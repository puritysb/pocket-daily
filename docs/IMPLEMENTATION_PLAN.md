연결한다. 텍스트 우선/이미지 우선/좌우 배치가 첫 수직 기능 단위이며, 이는
P4 전체 완료가 아니다. 과거의 “P1 실기기 통과 전 UI 확장 금지” 순서 대신
현재 사용자 요청에 따라 로컬 기능 구현은 진행하고 실기기 수용은 별도 미완료
조건으로 유지한다. 전송 실험·업로드·네트워크 변경을 재개하지 않는다.

현재 실행 경계 (2026-09-22): 사용자의 반복 업로드·연결 변경 중단 요청에 따라
실기기 조회/업로드/네트워크 변경 없이 로컬 코드·모의 전송·호스트 렌더링을
진행한다. P1/P2/P6 하드웨어 합격 조건은 남겨 두되, 이를 매번 펌웨어 업로드를
재개하는 이유로 삼지 않는다. 아래 누적 기록의 과거 “미구현”은 당시 상태다.
현재는 콘텐츠 준비·활성화·표시 응답과 Swift 편집/배포 경로가 연결되어 있으며,
카드 편집기에 오프라인 기준 렌더링을 추가했다. 기준 미리보기는 연결된 기기의
설정과 일치한다고 주장하지 않는다. 제품 완성에는 저장 공간/보관 정책, 제한 UI
정의 확장, 쓰기 승인, 실제 X3/X4 수용 검증 등 남은 요구사항을 충족해야 한다.

2026-09-22 후속 결정: 콘텐츠를 보여 주기 위해 File Transfer 세션을 종료하지
않는다. 현재 펌웨어의 일반 종료와 Nearby 종료는 모두 재부팅 경로를 갖고 있어,
STA에 `session/end`를 확대하는 것만으로는 반복 재연결 문제가 생긴다.
선택된 편집 세션 안에서 기존 서버를 유지하고 경량 콘텐츠 보기로 화면만
전환하는 방향으로 구현한다. 세션 종료는 별도 사용자 동작이다. 공용 검증
표시 모델 `ContentViewState`를 분리해 기존 Pocket 화면에 연결했으며,
라이브 화면 호스팅·표시 완료 응답·Swift 연결은 후속 로컬 구현에 포함됐다.
실기기 접속/업로드는 하지 않고 로컬 구현을 진행한다. 이 작업은 아래
P1/P2/P6 실기기 수용 조건을 면제하거나 전송 원인이 해결됐다는 뜻이 아니다.

- CrossPoint는 읽기·렌더링·입력·저장·절전·설치의 기반으로 유지한다.
  Pocket 전용 세션과 패키지 계층을 얇게 추가하고, 기반 코드 수정은 계측으로
  확인된 병목이나 필요한 수명 관리 경계에 한정한다.
- 제품의 기본 경로는 기존 공유기에 연결하는 STA다. USB, 핫스팟 전환,
  상시 연결 또는 기기 위치 변경을 성공의 전제로 두지 않는다.
- 변경을 세 종류로 나눈다: 콘텐츠는 콘텐츠 리비전, 지원되는 외형·배치는
  UI 리비전, 새로운 동작·드라이버·프로토콜은 펌웨어로 전달한다.
- 첫 완성 단위는 **카드 하나 편집 → 변경 파일만 전송 → 기기 적용 확인 →
  실패 시 기존 카드 유지**다. 범용 화면 편집기보다 이 경로를 먼저 완성한다.
- 완료 상태는 전송 완료 / 검증 완료 / 활성화 확인 / 펌웨어 재부팅 후 설치
  확인으로 나눈다. 응답 유실은 성공이나 실패로 추측하지 않고 확인 불가로 둔다.
- 정상 제품에서는 펌웨어 설치의 기기 확인을 유지한다. 무인 반복 설치는
  명시적 개발 모드에만 둔다. 콘텐츠·UI 자동 동기화도 사용자가 선택한 세션과
  대상에 한정하며 저장할 때마다 곧바로 기기를 변경하는 기본 동작은 만들지 않는다.

| 순서 | 결과물 | 다음 단계 진입 조건 |
| --- | --- | --- |
| P0–P1 | 재현 가능한 기준선, 병목 측정, 기본 전송 경로 결정 | 대용량 3회 해시 일치·재부팅 없음·중단 복구 |

주변 기능 확장은 보류하며 기존 제품 경로의 통합·수정·검증에 집중한다.

실행 기록 (2026-09-21): P0/P1 착수. 펌웨어 저장소에 검증된 게시·다운로드
SHA 비교·시험 파일 정리를 포함하는 HTTP/스트림 비교 도구를 구현했다.
Python 25개 테스트 통과. X3에서 두 경로의 1 KiB 전송은 통과했지만 HTTP
연결 및 이후 256 KiB 시험의 상태 조회가 간헐적으로 시간 초과됐다. 큰 파일
비교나 기본 경로 결정은 아직 완료되지 않았다. 상세는 펌웨어 저장소의
`docs/TRANSFER_BENCHMARK.md`. P2 이후는 미완료다.

현재 코드 감사에서 확인한 후속 수정 항목:

- P2 부분 구현 (2026-09-22): 선택적 AgentDeck 실시간 명령 큐를 연결 수명으로
  제한했다. 첫 명령에서만 버퍼를 할당하고 연결 종료/교체에서 해제하며,
  연결 전 명령과 잘리는 명령을 거부한다. 카드·SD 선택 outbox는 변경하지 않는다.
  전체 공유 상태 분리, 실기기 메모리·반복 세션 검증은 여전히 남아 있다.
- 수정됨 (2026-09-21): `Sources/Studio/UiPackEncoder.swift`가 레지스트리의
  int/bool/float 타입을 기록한다. typed 입력과 기존 정수 편집기 입력을 지원하고
  타입 불일치, 정수 범위 초과, 비유한 실수, 잘리는 메타데이터를 거부한다.
  같은 전체 바이트 fixture를 Swift 인코더와 기기 C++ 파서/metrics 적용 시험에
  고정했다. 이는 host 계약 검증이며 실기기 UI 적용 검증은 아니다.
- 수정됨 (2026-09-21): `applyThemePack`와 되돌리기는 동일 기기·정확한 활성
  팩 버전을 확인한 뒤 성공으로 처리한다. 조회 실패는 확인 불가로 표시하며
  이전 화면 캡처가 새 화면임을 주장하지 않는다. 배포 버전은 초 단위 시각 대신
  16자리 UUID 유래 토큰으로 구분한다. 응답 유실을 포함하는 트랜잭션 전체 복구는
  여전히 P3의 범위다.
- P3 부분 구현 (2026-09-22): UI 팩 선택을 CRC/세대 번호 이중 슬롯으로 기록하고
  쓰기·재읽기 확인 후 런타임 설정을 교체한다. 부팅 시 최신 팩 로드 실패는 이전
  기록으로 복귀하며 명시적 되돌리기는 이전 팩을 되살리지 않는다. 앱은 고유 팩
  파일명으로 이전 활성 파일을 보존한다. 설정 합성은 매번 네이티브 테마를
  기준으로 하며 저장 후 추가 할당 없이 준비된 버퍼를 인수한다.
  여러 자산의 트랜잭션, 보관 개수 제한,
  실제 전원 차단 시험은 아직 남아 있다. UI 팩 전체 기능 완료가 아니다.

## 1. 목표와 완료의 의미

CrossPoint의 읽기·하드웨어·저장·설치 기능을 유지하면서 Pocket Daily 앱에서
콘텐츠와 UI를 편집하고, 같은 Wi-Fi에 연결된 기기에 안전하게 적용한다.
일상적인 변경은 데이터 배포로 처리하고 실행 코드 변경에만 펌웨어를 사용한다.

첫 제품 완료 시나리오:

1. 사용자가 기기에서 동기화를 시작하면 저장된 Wi-Fi에 연결된다.
2. 앱은 기존에 확인한 기기를 다시 찾고 지원 기능·현재 리비전을 확인한다.
3. 카드 콘텐츠나 지원되는 화면 구성을 편집하고 적용을 누른다.
4. 변경된 파일만 전송하고, 기기가 검증한 뒤 활성 리비전을 전환한다.
5. 앱이 실제 적용 결과를 확인한다. 실패하면 이전 정상 리비전이 유지된다.
6. 개발 세션에서는 연결을 유지한다. 일반 세션은 완료 후 원래 화면으로
   돌아가고 무선 자원을 반환한다.

USB·핫스팟·클라우드 계정은 이 경로의 전제가 아니다. 잠든 무선 비활성 기기를
앱이 언제든 깨울 수 있다는 약속은 하지 않는다. 일반 제품의 펌웨어 설치는
기기 확인을 유지하고, 자동 설치는 명시적으로 선택한 개발 모드에 한정한다.

## 2. 출발점: 검증 사실과 공백

- X3에서 `w67fff974`의 6,030,416바이트 무선 전송, CRC 검증, 개발용 설치,
  동일 기기·정확한 버전 확인과 자동 저장 Wi-Fi 복귀가 성공했다.
- 설치 후 64 KiB 수신도 성공했지만 약 2.2 KiB/s였다. 낮은 힙 여유와 느린
  속도의 인과관계는 아직 확정하지 못했다. X4와 실제 앱 전체 경로는 미검증이다.
- 앱에는 전송 중 부가 요청 중단, 크레딧 기반 전송, 제한된 재시도·기기 ID
  확인이 있다. 펌웨어에는 COMPANION 프로필과 전송 자원 우선권이 있다.
- UI 팩은 범용 UI 런타임이 아니다. `UiPackStore.cpp`의 `loadPackFromSd`는
  최대 128바이트 읽기로 순차 무결성 검사와 레코드 해석을 수행한다
  (2026-09-22 로더 통합). 기존 8 KiB 제한과 포함 폰트 자산 거부는 유지한다.
  시작 시 적용은 `applyStartupPack`의 테마 수치 적용 중심이며 실기기 검증은 남아 있다.
- UI 팩 상태에는 이중 슬롯 기록과 재읽기 확인이 부분 구현됐다. 파일 전송
  commit과 여러 파일로 구성된 UI 리비전의 전원 차단 안전성은 별도 문제다.
- 기존 설계 문서의 “미구현” 머리말과 부분 구현 기록은 혼재한다. 계획 시작 시
  기능별 구현/로컬 검증/실기기 검증 상태를 다시 표시한다.

실기기 상세 증거는 펌웨어 저장소 `docs/CORE_CONNECTIVITY_REPAIR.md`,
구조 비교는 `docs/UPSTREAM_CONNECTIVITY_COMPARISON.md`를 따른다.

## 4. 단계별 실행

### P0 — 기준선과 계약 목록 고정

작업:

- 두 저장소의 기존 변경을 목록화하고 이번 계획의 변경과 구분한다.
- 소스 상태, 이미지 SHA, SDK 실효 설정, 설치 버전을 재현 가능한 기준선으로
  기록한다. 커밋하지 않은 변경도 식별 가능한 diff/빌드 기록으로 남긴다.
- 기능별 구현·테스트·실기기 상태표를 만든다. 과거 설계 문구를 구현 사실로
  취급하지 않는다. 원래 이미지와 SD 복구 방법을 보존한다.
- 패키지 버전, 기능 협상, 기기 식별, 전송·검증·활성화·설치의 계약을 목록화한다.

통과 조건: 현재 성공 경로를 다시 실행할 수 있고, 실제 동작과 계획을 구분할 수
있다. 이 단계에서 업스트림 대규모 병합, 파티션 변경, 기능 삭제는 하지 않는다.

### P1 — 병목 계측과 전송 경로 결정

작업:

- 작은 고정 크기 카운터로 수신 대기, SD 쓰기, ACK 대기, 서비스 호출 간격,
  free/minimum/largest/DMA heap을 구분한다. 큰 로그 링이나 병행 폴링은 금지한다.
- 동일 X3·SD·공유기·위치에서 기존 HTTP 업로드와 포트 82를 비교한다.
  현 포크의 HTTP 경로도 수정되어 있으므로 “순정 CrossPoint 대조군”이라고
  부르지 않는다.
- 1 KiB → 256 KiB → 약 6 MB의 무해한 데이터로 크기를 늘린다. 지원되는
  다운로드 경로로 결과 해시도 확인한다. 시험 파일은 명시적으로 정리한다.
- 각각의 비교에서는 전송 경로, 페이싱, Wi-Fi 버퍼 설정 중 한 변수만 바꾼다.
  계측 부담도 비교한다. 불필요한 플래시는 하지 않는다.
- 안정성·처리량·최대 메모리 사용을 근거로 앱의 기본 전송 경로 하나를 선택한다.
  기존 클라이언트/펌웨어 호환 어댑터는 유지한다.

통과 조건: 성공 후보는 대용량 전송 3회, 해시 일치, 재부팅 없음, 의도적 중단
복구를 통과한다. 속도 기준은 안정 대조군 실측 후 별도로 확정한다. 현재의
2.2 KiB/s를 제품 합격선으로 삼거나 근거 없는 개선 배수를 약속하지 않는다.
원인을 구분하지 못했으면 UI 기능을 추가하지 않고 필요한 계측을 보완한다.

주요 위치: 펌웨어 `web/UploadStreamServer.*`, `web/SocketReceive.h`,
`CrossPointWebServer.cpp:338`, `CrossPointWebServerActivity.cpp:673`,
`scripts/pocket_put.py`; 앱 `Sources/CrossPointClient.swift`.

### P2 — 동기화 세션과 자원 수명 정리

작업:

- 읽기 → 준비 → 연결 → 전송 → 검증/적용 → 복귀의 상태 전이를 명시한다.
  펌웨어 설치는 별도 분기로 분리한다. 취소·실패·시간 초과마다 해제 책임을 둔다.
- 공유 카드 상태와 외부 제공자 연결 상태를 분리한다. `AgentDeck::g_state`
  (`src/agentdeck/protocol.cpp:20`) 전체 삭제 대신 필요한 상태를 SD에서 복구하고,
  비활성 제공자의 큐·버퍼 수명을 실제 세션으로 제한한다.
- COMPANION 세션은 브라우저 관리 화면, 외부 제공자, 화면 스트림을 기본적으로
  띄우지 않는다. 기존 File Transfer와 직접 연결 기능은 별도 경로로 보존한다.
- 최대 연속 블록을 포함한 자원 예산과 시작/중단 기준을 P1 측정에 근거해 정한다.
  단순히 free heap 문턱을 낮춰 기능을 활성화하지 않는다.
- 앱에서 세션 상태·재접속 정책을 `PocketModel`에서 점진적으로 분리한다.
  기존 전송 동작을 유지하면서 이동하며, 한 번에 전체 앱 구조를 바꾸지 않는다.
- 저장된 주소 우선 확인 후 제한된 LAN 재탐색을 한다. ID가 달라지면 재개하지
  않는다. mDNS·BLE가 항상 가능한 것으로 가정하지 않는다.

통과 조건: 진입/복귀 10회와 30분 유휴 시험, 반복 전송에서 메모리의 누적 감소나
재부팅이 없다. 기존 읽기·오프라인 카드·수동 File Transfer 회귀가 없다.
개발 세션은 유지되고 일반 세션은 무선 자원을 반환한다. 이는 초기 합격 시험이며
장기간 안정성을 증명하는 수치는 아니다.

  차등 업데이트는 이 단계에서 도입하지 않는다.
- 패키지를 제한된 버퍼로 순차 검증한다. 경로 탈출, 중복 경로, 개수·크기·정수
  오버플로, 공간 부족을 거부하고 네트워크 입력으로 전체 팩을 할당하지 않는다.
- 새 리비전은 별도 위치에 완성한다. 이전 리비전을 보존하고 검증 후 활성 포인터를
  전환한다. 체크섬·세대 번호를 갖는 이중 기록 등 복구 가능한 commit 방식을
  저장소 특성에 맞춰 정하며, FAT rename 하나만으로 전원 차단 안전성을 주장하지 않는다.
- 앱은 활성 리비전·해시를 확인하고 성공 처리한다. 응답 유실 시 상태 조회로
  판단하며 불명확한 활성화 명령을 무조건 반복하지 않는다.

통과 조건: 작은 편집에 전체 콘텐츠나 펌웨어를 보내지 않는다. 손상 팩, 공간 부족,
연결 끊김, 중복 요청에서 기존 리비전을 보존한다. 활성화 단계별 장애 주입으로
기동 시 이전 또는 완성된 새 리비전만 선택함을 검증한다. 실제 전원 차단 시험은
SD 복구 준비 후 사용자 협조로 진행한다. 중간 리비전의 파일을 섞어 표시하지 않는다.

계약: 펌웨어가 소유하는 새 패키지 계약 문서와 양쪽 golden fixture를 함께 만든다.
기존 `.uipack` v1을 같은 버전 번호로 다른 의미로 바꾸지 않는다.

### P4 — 제한된 UI 정의와 호스트 미리보기

작업:

- 최초 지원 화면은 Pocket 홈/카드 목록/카드 상세로 제한한다. EPUB 읽기 엔진과
  복구·설정 필수 화면은 네이티브 기본 구현을 유지한다.
- 텍스트, 이미지, 제한된 행/열 배치, 목록, 여백과 사전 구현된 명령을 제공한다.
  노드 수·중첩·문자열·이미지·글꼴 캐시의 상한을 명시한다. JavaScript/Lua,
  임의 네트워크 호출, 임의 파일 접근은 도입하지 않는다.
- 현재 테마 팩을 깨지 않는 새 스키마/명시적 버전을 설계한다. 폰트 설치는 기존
  CrossPoint 형식·검증 경로를 재사용하고 리소스 파일로 분리한다.
- 같은 레이아웃·렌더링 코드를 호스트에서 재사용하고 기기·호스트 출력의 golden
  비교를 한다. 호스트 전용 디바이스 이미지/툴을 앱에 복사하지 않는다.
- 편집 미리보기는 로컬에서 처리하고 기기 캡처는 적용 후 요청 시 사용한다.
  실제 프레임과 미리보기를 UI에서 구분한다.

통과 조건: 순서·배치·문구를 바꿔도 플래시 없이 반영된다. 지원하지 않는 명령·팩은
안전하게 거부한다. X3/X4 크기와 회전, 긴 한글, 누락 자산, 메모리 부족을 검증한다.
잘못된 팩은 기본 UI 또는 이전 팩으로 복귀하며 필수 복구 화면을 잃지 않는다.

### P5 — 개발용 펌웨어 반복 작업과 제품 보안

작업:

- 검증된 빌드 → 대상/호환성 확인 → 전송 → 이미지 검증 → 명시적 개발 설치 →
  재부팅 → 재탐색 → 동일 기기·정확한 버전 확인을 하나의 개발 명령으로 묶는다.
- IP 변경, 부팅 지연, 응답 유실을 분리해 표시한다. 플래시 명령은 불명확한 응답을
  이유로 자동 반복하지 않는다. 실패 시 기존 SD 복구 경로를 안내한다.
- 기기 ID·CRC·해시는 인증이 아니라는 경계를 명시한다. 제품의 공유 LAN 쓰기
  기능에는 기기 측 승인으로 발급한 자격과 재전송 방지, 폐기/초기화 절차가 필요하다.
  구체 프로토콜은 자원 예산과 위협 모델 검토 후 계약으로 확정한다. 자체 암호를
  만들지 않는다. 승인된 제한 세션/폐쇄된 실험과 제품 배포를 구분한다.
- 개발용 원격 플래시가 제품 빌드에 노출되지 않는 것을 확인한다. 일반 사용자
  펌웨어 설치의 기기 확인은 유지한다. 파티션·부트로더·펌웨어 자동 롤백은
  현 검증만으로 지원한다고 표시하지 않는다.

통과 조건: 구별 가능한 두 개발 빌드의 앱/CLI 설치·복귀 반복 검증, 다른 기기·
손상 이미지·승인 없는 요청 거부, 사용자 취소와 제한 시간 동작을 확인한다.
보안 계약과 검증 없이 제품 자동 설치 기능으로 승격하지 않는다.

### P6 — 통합 수용 시험과 기본 경로 승격

- 실제 iOS/macOS 앱 × X3/X4에서 콘텐츠, UI, 개발용 펌웨어 경로를 검증한다.
- 네트워크 재연결, DHCP 주소 변경, SD 부족·제거, 중단 재개, 장시간 유휴와
  반복 세션을 시험한다. 하드웨어가 없으면 해당 기종은 미검증으로 남긴다.
- 앱 테스트·양 플랫폼 빌드, 펌웨어 host/Python 테스트·default 빌드·strict
  cppcheck, 제품 빌드 검증을 수행한다. UI 변경 단계에서는 스크린샷을 갱신한다.
- 새로운 경로는 capability로 선택하고 기존 전송/수동 복구 경로를 유지한다.
  구형 호환 경로는 실제 사용 중단 근거가 생기기 전 삭제하지 않는다.
- 실제 검증 결과만 두 저장소의 메모리에 기록한다. 커밋·푸시·릴리스·스토어
  제출은 별도 사용자 요청 없이는 수행하지 않는다.

## 5. 실행 순서와 첫 작업 묶음

의존 순서: **P0 → P1 → P2 → P3 → P4 → P6**.
P5의 보안 설계는 P2/P3 계약에 반영하고, 개발 자동화 완성은 P2 이후 별도 검증한다.
P3/P4는 승인된 개발 환경에서 먼저 시험하며 제품 수용에는 P5 보안 통과가 필요하다.

처음 착수할 작업은 다음 세 묶음이다. 각 묶음은 독립 diff와 검증 결과를 남긴다.

1. 기준선·기능 상태표·시험 데이터·결과 형식을 준비한다. 동작은 바꾸지 않는다.
2. 저비용 계측과 전송 비교를 수행해 병목 및 기본 경로의 결정 근거를 남긴다.
3. 측정 결과에 맞춘 자원 소유권 분리 한 가지를 적용하고 동일 시험을 반복한다.

이 세 묶음이 통과하기 전에는 범용 UI 편집기, 상시 화면 스트림, 새로운 전송
프로토콜, 추가 네트워크 태스크를 늘리지 않는다. 일정은 P1 결과와 필요한
실기기 가용성을 확인한 뒤 추정한다.

## 6. 이번 계획에서 하지 않는 일

- ESP-IDF 전면 재작성, 무조건적인 업스트림 병합, SDK/타이머/스택 크기 일괄 축소.
- 클라우드 계정·서버를 필수로 만드는 구조, 기본 핫스팟 전환, 상시 무선 대기.
- 기존 기능의 일괄 제거, 파티션/부트로더 변경, 검증되지 않은 자동 롤백 약속.
- 독립 실측 없이 전송 지연·재시도 횟수를 계속 조정하는 방식의 완료 선언.

유지할 원칙: **기기는 안정적인 실행기, 앱은 제작·배포 도구. 데이터 변경은
데이터로 전달하고, 동시에 필요한 자원만 보유한다.**

## 7. 실행 가능한 작업 단위와 판단 기준

아래는 후속 구현의 순서이며 완료 보고가 아니다. 현재 전송 병목의 원인은
확정되지 않았다. TCP 재전송 관찰만으로 무선 신호, 수신 자원, SD 처리 중
어느 하나를 원인으로 단정하지 않는다.

| 작업 단위 | 주 저장소 / 산출물 | 검증 및 종료 기준 |
| --- | --- | --- |
| A. 기준선 확정 | firmware: 설치 이미지·소스·계측 버전 대응표 | 빌드 성공과 설치 확인을 분리하고 동일 기기의 실제 버전 확인 |
| B. 전송 원인 분리 | firmware: 비교 실험·카운터·최소 수정 | P1 통과. 실패하면 다음 UI 기능 대신 가설 하나와 추가 실험을 선택 |
| C. 단일 세션 | 양쪽: 연결·전송·적용·복귀 상태와 자원 소유권 | P2 통과. 취소/실패에서도 서버·버퍼·Wi-Fi 해제 책임이 명확 |
| D. 카드 하나 배포 | 양쪽: manifest·변경 파일 전달·활성 리비전 확인 | 실제 앱 편집이 기기에 반영되고 실패 시 이전 정상 카드 유지 |
| E. 제한 UI 확장 | firmware: 검증/렌더링, app: 편집/미리보기 | 값 범위·합성된 배치 검증, 기기 출력 비교, 잘못된 팩 복구 |
| F. 개발 배포 자동화 | firmware 도구 + app 상태 표시 | 대상 확인부터 재부팅 후 정확한 버전 확인까지 한 명령, 불명확한 플래시 재시도 금지 |
| G. 제품 수용 | 양쪽: 승인·호환성·실기기 시험 기록 | P5 보안 및 P6 통과. 확보하지 못한 기종은 미검증 유지 |

### B의 실험 분기

- SD 쓰기/닫기 시간이 지배적이면 저장 경로와 쓰기 단위를 한 가지씩 비교한다.
- 서비스 호출 공백이 지배적이면 읽기·렌더링·외부 제공자와의 실행/자원 경합을
  조사한다. 태스크나 서버를 추가하는 것은 기본 처방이 아니다.
- TCP 재전송이 계속되지만 위 시간이 작으면 수신 버퍼·힙·네트워크 설정과
  호스트 송신을 분리해 검증한다. 페이싱 조정만으로 원인 해결을 선언하지 않는다.
- HTTP가 안정성과 자원 예산을 충족하면 기존 HTTP 경로를 기본으로 재사용한다.
  포트 82가 명확히 우수하면 그 경로 하나를 유지한다. 둘 다 실패하면 기본 경로
  선정을 보류한다. 업스트림 재사용과 기존 커스텀 전송 유지 중 어느 것도 선결하지 않는다.

### 자동화의 사용자 경험 경계

일반 사용자는 기기에서 동기화를 시작한 뒤 앱에서 적용 한 번으로 콘텐츠/UI의
전송·검증·활성화 확인을 끝낸다. 명시적으로 켠 개발 세션에서는 이후 반복
빌드·배포·재접속 확인을 자동화한다. 기기가 잠들거나 무선이 꺼져 있으면
앱은 대기/사용자 조치 필요로 표시한다. USB 연결, Mac의 Wi-Fi 전환, SD 교체를
정상 반복 흐름에 넣지 않는다. SD는 최초 부트스트랩 또는 복구 수단으로 남긴다.

각 작업의 인수인계에는 변경 파일, 양쪽 계약, 자동 시험, 실제 기기 결과,
미검증 항목을 남긴다. 일정과 처리량 목표는 B의 재현 가능한 기준선 이후 정한다.
