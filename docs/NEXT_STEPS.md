# Pocket Daily 체크포인트와 남은 작업

기준일: 2026-09-24 (반복 Apply 수정·Mac 스튜디오 1단계 반영). 릴리스 완료 선언이
아니라 다음 구현을 위한 인수인계다.
지침은 각 저장소의 `AGENTS.md`, 상세 계약은 기존 설계 문서를 따른다.

## 확보한 기준선

- 앱: 콘텐츠·이미지·지원 배치·테마 편집, 로컬 미리보기, 변경분 배포,
  저장 활성화와 화면 완료의 분리, 세션 한정 live apply 구현.
- 펌웨어: 전용 Pocket Daily Sync, 같은 Wi-Fi/명시적 직접 연결 안내,
  복구 가능한 콘텐츠 활성화, 제한된 폰트 렌더링, 게임 제거.
- X3/Mac 같은 Wi-Fi: 정리본 `wbcb431b1` 무선 설치 및 전용 Sync 자동 복귀,
  앱 연결과 최초 카드의 `rendered` 응답 확인. 추가 재연결 없이 편집 전송과
  활성화도 성공했지만 두 번째 화면 갱신은 메모리 부족으로 실패했다.
- 원래 콘텐츠는 generation3으로 복원됐고 로컬 초안은 보존됐다.
  새 실물 화면 확인은 하지 않았다. 기기의 `rendered` 응답은 광학 검증이 아니다.
- 로컬 검증: Swift 267개, 펌웨어 호스트 359개, iOS/Mac 빌드,
  default 펌웨어 빌드·엄격한 정적 검사 통과. iPad iOS27 편집기 UI 시험
  1건은 여전히 실패하며, iOS26.5의 관련 시험 통과로 대체하지 않는다.

## 2026-09-24 후속 결과

- 반복 Apply 메모리 부족 원인: 리더가 모든 HTTP 응답 연결을 먼저 닫아
  lwIP TIME_WAIT PCB(120초, 약 256B, 최대 16개)가 쌓였다. 펌웨어 Sync가
  자기 포트(80/82)의 TIME_WAIT만 해제하도록 수정했다(펌웨어
  `docs/sync-route-memory.md`). 안전 기준 16KiB/4KiB는 그대로다.
- X3 w0482f45b, 실제 Mac 앱 편집 전송: gen4 `rendered`(17,524B/8,180B),
  같은 세션 두 번째 gen5 `rendered`(20,428B/13,300B). 기기 receipt이며 카드별
  광학 확인은 따로 기록되지 않았다. X4·직접 연결·장시간 유휴는 미검증.
- 사용자 테스트에서 "Apply" 버튼 3개(읽기 설정·테마·카드) 혼동이 확인됐다.

## Pocket Daily 프로필 (방향 전환, 2026-09-24)

목적은 카드 전송이 아니라 앱에서 Pocket Daily 자체의 배치와 기능을 설정하는
것이다. 현재 홈 구성·기능 동작은 펌웨어 C++에 하드코딩되어 있고 데이터로
바뀌는 것은 테마 수치(63개)와 읽기 설정 4개뿐이다.

- 1순위: 홈 섹션 순서/배치와 주요 기능 On/Off(이어보기, 학습 카드, 모니터링 위젯 등).
- 2순위: 슬립 화면 구성(잠잘 때 보여줄 화면 모드).
- P0 완료(펌웨어 `docs/pocket-profile-v1.md`). P1-1 기기 표시 상태 동기화 완료:
  X3 캡처와 앱 렌더 0픽셀 차이. 다음은 P1-2 프로필 저장·적용·모니터링 카드.
- P1-2 완료(펌웨어 8dd436d1): 프로필 저장·적용, 슬립 화면, 깨어남 띠. P2 Mac
  Home & Sleep 편집기 구현(배치 구조 미리보기, 순서/켜기, 날씨, 슬립, Send).
  iPad/iPhone 확장은 U4에서 완료.
- P1-3 파이프라인 완료(리더 없이, 2026-09-25): 펌웨어 Home/Daily Brief 그리기를
  기기·호스트 공용 렌더러(`src/pocket_daily/home/`)로 분리하고 호스트 ABI
  `pdui_render_home`/`pdui_render_brief`(ABI 1, 추가만)로 내보냈다. Mac Home & Sleep
  캔버스는 이 렌더러가 그린 샘플 데이터 프레임을 표시하고(“Sample data” 표기),
  렌더러를 쓸 수 없으면 배치 구조도로 돌아간다. 남은 것: 리더 충전 후 캡처 비교로
  픽셀 오차 보정(호스트 헤더는 테마 헤더가 아닌 단순 헤더, 표지는 빗금 대체, 아래
  날씨 패널의 현재 기온 영역 비는 경우, 호스트 `buildRows`의 `collectOverview` 중복)과
  그 뒤 골든 해시 고정.
- UX 부채: 카드 삭제 되돌리기는 해결(인라인 Undo·⌘Z). 리더에 있는 카드를
  앱으로 다시 불러오는 기능 구현(2026-09-25, 펌웨어 `docs/content-read-v1.md`):
  Cards의 "Load cards from the reader…"가 게시된 파일을 읽고 해시를 검증한 뒤
  가져오기 검토 화면으로 연다. 실기기 확인 대기.
- P0 펌웨어 하드코딩 인벤토리 → P1 검증된 프로필 형식·재플래시 없는 적용·호스트
  렌더러의 홈 렌더링 → P2 Mac 스튜디오 캔버스에서 편집 후 Send. 두 저장소 계약
  변경이므로 양쪽 검증이 필요하다.

## 다음 구현의 시작점

펌웨어 `ContentPresentation::service`의 기준은 총 여유 16,384B와
최대 연속 블록 4,096B다. 최초 적용은 16,448B/10,740B로 통과했지만,
다음 적용은 14,184B/7,156B, 복원은 13,140B/8,180B로 거절됐다.
나중 유휴 상태에서 일부 메모리가 회복됐으므로 영구 누수로 단정하지 않는다.

`CrossPointWebServerActivity`, `UploadStreamServer`, Arduino WebServer의
요청/소켓 수명, 폰트·카드 객체의 해제를 단계별로 대조한다. 측정 자체가
상시 할당이나 로그 부하를 늘리지 않도록 한다. 기존 카드 snapshot과 폰트의
해제 코드가 있다는 사실만으로 전체 세션의 회수를 입증한 것은 아니다.
원인·수정·회귀 시험이 확보된 뒤 필요한 한 번의 실기기 검증을 진행한다.

안전 기준 낮추기, 상시 버퍼 추가, 자동 재부팅, 반복 재설치, 무단 Wi-Fi
전환은 해결책으로 사용하지 않는다. 핵심 경로가 통과하기 전 주변 기능은 확장하지 않는다.

## 재현과 저장소 경계

- 앱과 펌웨어는 각각 별도 커밋한다. 빌드·기기 로그와 펌웨어 바이너리는
  커밋하지 않는다. 앱의 고정된 호스트 렌더러·미리보기 폰트는 제품 자산이다.
- 펌웨어 SDK의 `filesystemType()` 변경은 `scripts/storage_sdk.patch`와
  빌드 전 적용기로 재현한다. 서브모듈 포인터를 임의의 로컬 커밋으로 바꾸지 않는다.
- 기기에 설치된 바이너리는 위 dirty-tree 버전 그대로다. 이후 체크포인트의
  Git SHA와 설치 버전이 같다고 주장하거나 커밋만으로 재설치하지 않는다.
- 이전 날짜의 메모와 로그는 이력이다. 현재 수용 상태는 이 문서와
  `PROJECT_MEMORY.md`의 최신 실기기 기록을 기준으로 판단한다.
